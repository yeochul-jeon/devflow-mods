# 오해 없는 글 (ASD-STE100 에서 착안, 80%)

## 적용 범위
전체 답변이 아니라 **실행·결정에 쓰일 부분**에만 적용한다. 배경 설명까지 이 규칙으로 쓰면 글이 토막 나서 오히려 읽기 어렵다.

## 지킬 것
각 규칙 아래 줄은 이유다. 규칙을 지켰는데 이유가 지켜지지 않았으면, 이유에 맞게 더 고친다.

- 한 문장에는 지시나 사실 하나만 쓴다. 동시에 해야 하는 행동만 예외다.
  지시 두 개를 "-고", "-말고", "-한 뒤" 로 잇지 않는다. "멈추고 담당 팀에 연락하세요" 대신 "멈추세요. 담당 팀에 연락하세요."
  이유: 읽는 사람은 한 문장을 한 단계로 실행한다. 한 문장에 지시가 둘이면 두 번째를 놓친다.
- 능동태로 쓴다. 누가 무엇을 하는지 보이게 쓴다.
  이유: 하는 사람이 안 보이면 읽는 사람은 자기가 할 일인지, 기다리면 되는 일인지 모른다.
- 조건이 있으면 문장 앞에 쓴다. "X 이면 Y 하세요."
  이유: 행동을 먼저 읽은 사람은 조건을 읽기 전에 실행한다.
- 같은 대상은 처음 쓴 이름으로 끝까지 부른다.
  이유: 읽는 사람은 다른 단어를 다른 대상으로 읽는다. 영어 이름과 한국어 번역어도 다른 단어다. `config.yaml` 이라고 썼으면 뒤에서 "설정 파일" 로 바꾸지 않는다.
- 명사를 3개 넘게 잇지 않는다. "설정 변경 요청 처리" 대신 "설정을 바꾸는 요청을 처리합니다".
  이유: 명사를 이으면 어느 명사가 어느 명사를 꾸미는지 읽는 사람이 추측해야 한다.
- 단계나 항목이 3개 이상이면 번호 붙은 세로 목록으로 쓴다.
  이유: 번호가 있으면 읽는 사람이 어디까지 했는지 잃지 않는다.
- 전문용어·식별자·명령은 원래 표기 그대로 쓴다. 명령은 코드 블록에 넣는다.
  이유: 읽는 사람은 명령을 복사해 실행한다. 번역하거나 풀어 쓴 명령은 실행되지 않는다.
- 비유·꾸밈말·감탄·수사 의문문은 쓰지 않는다.
  이유: 비유는 읽는 사람마다 다르게 풀린다. 실행할 글에서는 그 차이가 실수가 된다.
- 한 문장은 25어절 이내로 쓴다.
  이유: 긴 문장에는 조건과 행동이 섞인다.

## 풀어 줄 것 (나머지 20%)
- ASD-STE100 승인 어휘 사전은 쓰지 않는다. 보통의 기술 어휘를 쓴다.
- 단계 뒤에 짧은 이유 한 문장을 붙여도 된다.

## 정확성
쉬운 문장이 사실을 틀리게 말할 수 있다. 명료함과 정확성은 따로 확인한다.

사용자가 준 글을 고쳐 쓸 때:
- 그 글의 수치·조건·예외를 지우지 않는다.
- 그 글에 없는 사실을 더하지 않는다. 글이 모호하면 빈칸을 지어내지 말고, 무엇이 빠졌는지 고친 글 밖에 적는다.

처음부터 쓸 때:
- 확실한 사실만 단계로 쓴다.
- 확실하지 않은 값(이름, 경로, 버전)은 `<app-name>` 같은 자리표시자로 두고, 무엇을 넣을지 적는다.

## 예시
예시 1. 모호한 글을 고쳐 쓴다.
```
전: 필요한 설정 변경 후 시스템 재시작을 진행해주세요.
후: 필요한 설정을 바꾸세요. 시스템을 다시 시작하세요.
```
고친 글 밖에 적는 메모: 어떤 설정을 바꿀지는 원래 글에 없습니다. 글을 준 사람에게 확인하세요.

예시 2. 이름을 하나로 맞추고, 명령을 코드 블록에 넣고, 조건을 앞에 쓴다.

전: `config.yaml` 수정 후 설정 파일 반영을 위해 `systemctl restart myapp` 으로 재시작하고, 재시작이 실패하면 `journalctl -u myapp` 로 로그를 확인하세요.

후:
1. `config.yaml` 을 수정하세요.
2. `myapp` 을 재시작하세요. `config.yaml` 을 반영하는 단계입니다.
   ```bash
   systemctl restart myapp
   ```
3. 재시작이 실패하면 `myapp` 의 로그를 확인하세요.
   ```bash
   journalctl -u myapp
   ```

## 이름 붙이기
이 글을 "ASD-STE100 준수" 라고 부르지 않는다. 규격 원문과 대조하지 않은 규칙이다. 필요하면 "ASD-STE100 에서 착안한 80% 문체" 라고 쓴다.
